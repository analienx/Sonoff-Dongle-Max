# SONOFF Ember → MR4U CC2674P10: ordered USB coordinator cutover

**Authoritative Python commands:** [P10_PYTHON_MIGRATION_WORKFLOW.md](P10_PYTHON_MIGRATION_WORKFLOW.md). This runbook specifies the operational sequence; the scripts execute only their narrowly documented steps. Last private baseline: 61 routers, 45 end devices, one coordinator and 21 groups. This is one existing Zigbee network, not a second network. Do not publish actual device IEEE addresses, network keys, backups or add-on options in the public repository.

**Hardware correction:** SMLIGHT's current SLZB-MR4U specification names the CC2674P10 **Radio 1** and EFR32MG26 Radio 2. Earlier instructions saying 'P10 = Radio 2' were mistaken. Ignore numeric radio order until the physical unit's port and the actual P10/ZNP firmware are confirmed. In this installation the user cannot attach the replacement to the HA USB host until the SONOFF is disconnected. Therefore **NO live P10 visibility from HA is required BEFORE the outage**. The TCP/LAN probe remains an optional alternative topology, NOT a USB cutover gate.

**Upstream references:** [Zigbee2MQTT migration FAQ](https://www.zigbee2mqtt.io/guide/faq/#how-do-i-migrate-from-one-adapter-to-another), [IEEE copying](https://www.zigbee2mqtt.io/guide/adapters/flashing/copy_ieeaddr.html), [serial by-id / adapter settings](https://www.zigbee2mqtt.io/guide/configuration/adapter-settings.html), [SMLIGHT MR4U product specification](https://smlight.tech/products/slzb-mr4u). Zigbee2MQTT cautions that Ember↔Z-Stack migration may require selective re-pairing and does not promise cross-stack no-repair recovery.

## Phase A. Prepare while the SONOFF remains online

1. Retain the existing **private hot** Zigbee2MQTT data-directory bundle, add-on options, device/group baseline and exact source SHA-256; verify it. Whole-HA backup is optional and is not needed for this coordinator migration. The hot bundle is provisional, not a replacement for the final cold capture. Observe critical switches, metering, groups, HA automations, route-error rates and which sleepy/relay-off devices should be excluded from the immediate response window. Freeze OTA/channel/TX/pairing experiments.
2. Confirm actual SONOFF source USB by-id path and add-on boot/watchdog status. The real Home Assistant installation has serial port, adapter and baudrate values in BOTH Zigbee2MQTT YAML and Supervisor add-on options; both layers must remain aligned. Ensure independent HA management/SSH access remains available even when Zigbee2MQTT is down. Do **not** unplug the SONOFF yet.
3. Run the **read-only** `p10_outage_freeze.py` plan with the current source config SHA and a fresh private cold ZIP path. Confirm normal source state and that the path is writable; never reuse or overwrite an earlier bundle. Read the canonical `analienx/config:skills/zigbee-coordinator-migration/SKILL.md`, HA local-executor and mutation-safety skills before live operations.

## Phase B. Take the final backup BEFORE the physical USB swap

4. At the authorized outage, run `p10_outage_freeze.py --execute --approval STOP_Z2M_FOR_MR4U_MIGRATION` with the *same* source SHA and fresh output. The script must verify **add-on stopped and final COMPLETE cold Zigbee2MQTT bundle integrity**. If it fails, leave the SONOFF attached and recover the existing Zigbee2MQTT operation. Never take the only recovery backup after removing the old radio; no full Home Assistant backup is required.
5. Only after a successful cold capture, physically disconnect/fully isolate the SONOFF radio from all power sources, **without resetting or reflashing it**. Stopping Z2M alone is not physical isolation. Preserve its network/NVRAM state intact for rollback. Do not allow two radios with the old coordinator IEEE/PAN/security identity to transmit simultaneously.

## Phase C. Connect MR4U to the HA USB host and identify P10

6. Connect the MR4U on the released HA USB connection; make sure its actual CC2674P10 radio is in the supported USB/ZNP coordinator mode and not held by another host, SMLIGHT hub or ZHA/Zigbee2MQTT instance. If only a management/debug USB interface appears, inspect its own UI/mode selector instead of guessing. Use `p10_usb_cutover.py discover --cold-bundle PRIVATE_COLD_ZIP` to enumerate **actual HA** `/dev/serial/by-id/…` paths and establish that the original SONOFF path is absent while Zigbee2MQTT remains stopped.
7. Use `p10_usb_cutover.py stage --cold-bundle PRIVATE_COLD_ZIP --out NEW_PRIVATE_STAGE --target-by-id EXACT_VERIFIED_HA_P10_PATH`. The script opens only that idle candidate, sends ZNP SYS_PING/SYS_VERSION, confirms the previously measured P10 revision, and creates original/target YAML and add-on-option pairs plus private hashes and the acceptance baseline. It NEVER programs the radio or changes HA config. Do not use Zephyrus COM4, `/dev/ttyACM0`, guessed socket port, 'Radio 2' or the first detected serial interface as identity proof.

## Phase D. Transfer the radio network state, then switch application

8. With the SONOFF isolated, use the separately reviewed **actual Ember-to-Z-Stack coordinator restore method** for the deployed Zigbee2MQTT/herdsman and MR4U firmware. Record privately and read back the **effective** old coordinator IEEE (factory/secondary IEEE caveat), PAN ID, extended PAN ID, Zigbee channel 11, existing network key/key sequence, suitable counters and Trust Center state. Do not assume an empty Ember `devices` field means all device keys can be reconstructed, or that a 400-entry TCLK allocation proves successful network restoration. If the target proposes a new network or mismatch, stop—do not erase `database.db`, reinitialize the home network or reset the original SONOFF. The Python staging/USB scripts do NOT implement this transfer.
9. When the above is independently verified, use `p10_ha_apply.py --phase target` first in dry-run mode, then execute only under its specific approval and operator evidence gates, updating **both** existing serial settings layers to the verified USB by-id path and `zstack`. Keep Z2M stopped during apply; verify old SONOFF absent and only one owner of the P10. Run the separately gated `p10_ha_start.py --phase target`, examine startup logs immediately, verify the existing network identity and check no accidental new-network formation or automatic reinitialization.

## Phase E. Functional acceptance and reverse USB rollback

10. Take a private post-start bundle and compare against the 106 non-coordinator devices and 21 groups with `p10_migration_workflow.py assess`. This measures fresh incoming reports, lost/changed device identities and groups, **not** guaranteed command delivery. Separately test bidirectional unicast, groupcast, metering, essential automations, targeted router joins/rejoins, TI coordinator missing-router check and routing/error rates across matching windows. Sleepy or intentionally relay-off devices need separate observation windows. Do not make repeated full-mesh network scans, mass re-pair devices or mistake total routers/TCLK table for 60 direct neighbors.
11. To rollback: STOP Zigbee2MQTT, isolate/unplug the MR4U **Zigbee P10 radio**, restore the exact source YAML **and** original add-on options with `p10_ha_apply.py --phase rollback`, reconnect the untouched SONOFF only once the target is isolated, then start via `p10_ha_start.py --phase rollback`. Verify critical devices. Do not blindly restore an earlier coordinator NVRAM or force stale security counters; targeted rejoins may be required following repairs during the trial. Keep all snapshots/logs private.
12. Once stable on the chosen coordinator, take a new *narrow* Zigbee2MQTT/coordinator backup and record hardware, firmware, effective IEEE, topology, repairs, group/HA behavior and measured errors. Keep the inactive radio isolated. A successful 61-router mesh does not alone prove a 60-direct-neighbor allocation.

**Progress boundary:** source hot backup/staging and outage dry run were exercised live previously; USB discovery, radio-state restore, cold capture, two-layer target application, post-cutover recovery and rollback have NOT been exercised on the actual replacement. Do not mark them passed until the cutover yields real evidence. If Zephyrus/HA access is absent, defer the *physical* swap rather than suggesting offline script tests established production readiness.
