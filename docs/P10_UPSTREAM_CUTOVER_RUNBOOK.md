# SONOFF Ember → MR4U CC2674P10: upstream-aligned cutover runbook

**Scope:** the existing single Zigbee2MQTT network; 61 routers, 45 end devices, 21 groups at the last private baseline. This document supplements `P10_CUTOVER_PREPARATION.md` and #29. **The production cutover has not happened.** Keep actual IEEE addresses, network keys, backup archives, credentials and private per-device results outside Git. The existing MR4U board's radio labels/port assignments must be confirmed on the physical unit, not inferred from generic MR4U marketing pages.

**Upstream references:** [Zigbee2MQTT migration FAQ](https://www.zigbee2mqtt.io/guide/faq/#how-do-i-migrate-from-one-adapter-to-another), [copy adapter IEEE](https://www.zigbee2mqtt.io/guide/adapters/flashing/copy_ieeaddr.html), [adapter TCP settings](https://www.zigbee2mqtt.io/guide/configuration/adapter-settings.html), [MQTT coordinator check and networkmap warnings](https://www.zigbee2mqtt.io/guide/usage/mqtt_topics_and_messages.html), [SMLIGHT multi-radio ports](https://smlight.tech/manual/slzb-06/guide/mr-series-specific). Zigbee2MQTT explicitly says Ember ↔ Z-Stack migrations MAY require device re-pairing and are not officially supported; no script can guarantee otherwise.

## A. Do now, without an outage

1. **Declare the single-network scope and success criteria.** Retain `database.db` identities, friendly names, MQTT discovery prefix, 21 groups/bindings, existing channel 11 and network PAN/extended PAN/key. Record representative functional tests (real command and report, group command, metering, automation, router joins, sleepy sensors) and existing route-error rates. Exclude intentionally relay-off bulbs from the immediate availability denominator; record a separate later observation window for sleepy devices. `p10_device_acceptance.py baseline`, `p10_capacity_gate.py`, `p10_neighbor_capacity.py` cover only parts of this; functional checks remain manual/live.
2. **Select a physical path for MR4U.** Prefer Ethernet/PoE, stable DHCP reservation/static address and a known power source. Use the actual SMLIGHT UI to identify CC2674P10 radio, its current coordinator firmware/mode and configured TCP socket. Different SMLIGHT pages and board generations use different radio numbering: *do not trust 'Radio 2 = 7638' without identity verification*. Disconnect the COM4 USB serial owner before opening the same radio over TCP; only one application owns its coordinator port. Check HA can reach this host and that no other ZHA/Z2M/OTBR or MR4U Zigbee Hub function owns that radio. `p10_target_endpoint.py` probes a P10's SYS_PING/SYS_VERSION FROM HA, but does not independently attest physical board/port ownership or coordinator network state. Do not form a household network during this check.
3. **Preserve source SONOFF.** Document exact SONOFF USB-by-id path, current USB and any separate Ethernet/USB/power paths, how to physically isolate Zigbee radio transmission, and how to bring it back without resetting/upgrading/erasing firmware or NVRAM. Note Z2M add-on autostart/watchdog and any other clients that could reopen the radio. Test the *isolation procedure* without powering down the existing network only where it can be safely observed; otherwise leave as a cutover operator check. Two devices claiming the same coordinator IEEE/network identity must never be active concurrently.
4. **Capture narrow recovery material.** Preserve the *complete Zigbee2MQTT data directory* (including custom converters/extensions, device and group definitions, `database.db`, `configuration.yaml`, `coordinator_backup.json`, `state.json` as present), the add-on configuration/options and the original radio's retained NV/network state. Include the existing network identity and counters privately; never manufacture coordinator link-key entries from the device database. A whole HA backup is OPTIONAL and is not a cutover gate. The current `p10_cutover_prepare.py capture` copies only a named subset and is non-atomic while Z2M runs: its snapshot is a checkpoint, NOT the final complete recovery copy. Zigbee2MQTT's native `bridge/request/backup` exports the data directory (excluding logs) but is also not a substitute for the final cold copy or an attested radio-state restore.
5. **Document actual backup/restore path.** Verify the exact installed Z2M/herdsman version can load the source unified Ember backup on this exact P10 firmware, retain existing coordinator IEEE and network/security parameters, and respond predictably on failure. Ember `devices=[]` can be expected; it neither proves a corrupt network nor proves all Trust Center data can be reconstructed. Verify how the active network frame counter, key sequence and trust-center behavior will be retained. Do not mutate the source coordinator to test target restoration. No firmware flash, NV erase or arbitrary backup edits as a startup workaround.
6. **Stage configs without deploying.** `p10_config_stage.py` makes an exact `rollback_configuration.yaml` and, once target TCP P10 identity is verified, proposes only `serial.port` and `serial.adapter` changes to `zstack`. Re-check baud/flow control, network identity, active add-on overrides/environment variables, any SOCAT or automatic adapter discovery. Keep the original config and private hashes outside Git. The renderer does NOT write the radio IEEE or restore a network.
7. **Plan rollback and explicit decision window.** Reserve time for the mesh to reform; agree which essential automations/lights must function and which sleepy-device checks can wait. Preserve old SONOFF *as-is*; rollback first reverses connections/config without blindly loading an older coordinator NVRAM image. Security counters may have moved, so rollback is not guaranteed to be an instant plug-swap. Keep a manual, documented targeted re-pair plan if cross-stack recovery fails.

## B. Actual cutover — deliberate maintenance window

8. **Freeze unrelated change and record baseline.** No OTA, channel/TX changes, mass pairing, route scans or other experiments at the same time. Record a cutover timestamp, live Z2M version, critical MQTT/Home Assistant integration health and a bounded route-error baseline. Check existing private artifacts can be read and their hashes match; ensure access to HA and the MR4U remains available independent of Zigbee.
9. **Stop Z2M; prevent automatic restart.** Confirm the add-on has stopped and released its serial port. Take the FINAL *cold, complete* Z2M data-directory and add-on settings snapshot here; verify identity, hashes, permissions and storage location. `p10_cutover_prepare.py capture` does not implement the complete-directory cold-copy requirement. Preserve original backup and device records; do not delete `database.db`/`coordinator_backup.json` if the intention is to keep this network.
10. **Physically isolate the SONOFF radio**, accounting for all possible power sources, while keeping its stored network untouched. Confirm it cannot continue acting as coordinator. Stopping Z2M alone does not prove that the radio has stopped transmitting. This is a hardware/operator step, NOT implemented by our Python scripts.
11. **Provision ONLY the selected MR4U P10 radio**, after its port and mode are independently verified. Restore source IEEE via a documented device-specific method; verify effective IEEE readback (secondary versus factory primary address matters), PAN ID, extended PAN ID, channel, network key, key sequence, network/security frame counters and required Trust Center state. Use the existing unified backup only through a verified exact-version restore path. Abort and retain source intact if the P10 starts an unexpected new network or asks to wipe the original backup. `p10_nv_lengths.py` measures 400 provisioned TCLK slots, NOT network restore or neighbor capacity.
12. **Deploy the staged two-line serial configuration via the approved HA mutation process**, ensure only the intended Z2M instance owns the P10 socket, and start once. Check logs for restored network (not new formation), actual active coordinator IEEE and network ID, and mismatch/security errors; stop before automatic retries/reinitialization can create an unintended new network. Keep the SONOFF isolated.

## C. Observe, accept or roll back

13. **Progressive service checks.** Confirm Z2M and MQTT bridge health; compare private `p10_device_acceptance.py compare` baseline with post-cutover `lastSeen` timestamps. This proves inbound reporting only; separately test *bidirectional* switching/dimming, group commands, metering and critical HA automations, direct/router-assisted joins and an intentionally selected test pairing. A device merely present in `database.db` is not a successful recovery.
14. **P10-specific check and stabilization.** Use Z2M's TI `bridge/request/coordinator_check` to identify missing routers (not a neighbor-capacity measurement). Record bounded paginated neighbor/LQI evidence and routing/source-route errors; don't launch repeated full network maps on a 100+ device mesh. Expect some transient route repair after a coordinator move and allow a meaningful observation interval. If a few routers fail, attempt selective power-cycling; consider *targeted* re-pairing with join limited to the coordinator as documented upstream. Every re-pair changes the rollback position; document any device affected, and do not start a mass re-pair while the rollback decision is open.
15. **Choose one outcome.** KEEP P10 only when critical functionality and acceptance criteria pass; otherwise STOP Z2M, isolate the MR4U's Zigbee radio (it may stay powered for Thread ONLY if Zigbee cannot transmit), restore exact source config and associated application data **only if necessary**, reactivate intact SONOFF, start Z2M once and verify core services. If security counters/rejoins reject the older radio, diagnose rather than repeatedly restoring older network state or launching two coordinators together. Preserve the post-attempt logs and snapshot privately.
16. **After stable keep or rollback**, take a new coordinator backup of the winning radio plus a fresh application snapshot; document new firmware, TCP/USB topology, frame counters, any repaired devices, group/HA automation behavior and current source-route/neighbor observations. Do not claim a 60-direct-neighbor allocation from 61 total mesh routers.
