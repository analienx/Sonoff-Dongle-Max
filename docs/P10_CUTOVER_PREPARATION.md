# MR4U CC2674P10 USB swap — preparation and evidence

**Use the current [Python USB cutover workflow](P10_PYTHON_MIGRATION_WORKFLOW.md) and [ordered runbook](P10_UPSTREAM_CUTOVER_RUNBOOK.md), not an earlier TCP-only migration note.** The user's Home Assistant USB connection is occupied by the production SONOFF; the MR4U is intentionally not visible from HA until the deliberate physical replacement. Do not insist on an HA-to-MR4U Ethernet probe while the SONOFF remains connected. Current SMLIGHT MR4U specifications identify CC2674P10 as Radio **1** and EFR32MG26 as Radio **2**; verify actual P10/ZNP firmware on the unit rather than trusting labels. The earlier 'P10 Radio 2' description was mistaken.

**Recovery material available:** a confidential full Zigbee2MQTT *hot/provisional* data bundle (255 regular files, about 31 MB, two recorded external symlink dependencies), private device/group baseline (61 routers, 45 end devices, one coordinator, 21 groups), exact rollback YAML and matching add-on options. The former named-file-only snapshot is not a complete recovery bundle; the full HA archives created on September 23/24 are OPTIONAL and not required for this coordinator migration. The previously measured idle P10 `SYS_VERSION` revision is `20260310`; the 400 TCLK slots measured on that radio are not proof of direct-neighbor capacity or network restore. The SONOFF source network key/IEEE/NVRAM are preserved privately and must never appear in Git.

**Workflow boundary:** run `p10_outage_freeze.py` in dry-run mode while the SONOFF is active. At the approved outage, STOP Zigbee2MQTT and verify the full COLD application/add-on-options archive *before* physically disconnecting the SONOFF. Then attach MR4U to HA USB; `p10_usb_cutover.py discover` enumerates actual HA by-id paths only after confirming the source USB is absent and the add-on remains stopped. Its `stage` probes the selected idle P10 via ZNP SYS_PING/SYS_VERSION and creates both USB target config layers plus exact rollback files from the cold bundle. It does not transfer coordinator IEEE/network/security state or apply live settings.

**Live activation boundary:** independently restore and read back the existing network identity/security state on the verified P10 while the SONOFF is isolated. Only then use `p10_ha_apply.py` and `p10_ha_start.py` with their explicit phase-specific operator confirmations. Verify actual bidirectional device communication, groups, joins and routing; database/lastSeen alone is inadequate. To rollback, stop Zigbee2MQTT, isolate P10 Zigbee, restore both source setting layers, reconnect intact SONOFF and start once. Never run two copies of the network concurrently, blindly rewind security counters, factory-reset the original SONOFF or erase the device database to suppress mismatches.

**Testing status:** previous preparation tests and read-only hot backup were exercised against HA; the NEW USB handoff and production radio-state restore can only be tested after the controlled physical replacement. No hardware cutover or rollback has yet occurred. A full HA backup is not a condition for proceeding, but an independently verified final COLD Zigbee2MQTT bundle is.
