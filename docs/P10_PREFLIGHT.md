# P10 candidate evaluation — separate from production SONOFF

Tracking: dedicated migration-preparation issue #29; context #18 and #28. This kit audits **the specifically identified SMLIGHT CC2674P10 board** (06P10, 06P10U or MR4U Zigbee radio), without changing Zigbee2MQTT, network identity, IEEE address, keys, NVRAM, channel, or pairing. Tested only with mocked ZNP serial frames until a P10 is physically connected.

## 1. Read-only identification on Zephyrus

Leave the SONOFF as the only production coordinator on the Raspberry Pi. Attach only the new P10 over USB to the laptop; do not attach it to the production Zigbee2MQTT owner or copy coordinator data. For Ethernet/USB models switch the SMLIGHT bridge to USB mode locally (this may interrupt its own Ethernet bridge), and identify its dedicated COM port. Do **not** run these scripts against the existing coordinator or a `socket://` URL. If the new device starts or broadcasts any preconfigured network after power-on, do not join it to the household mesh.

```powershell
py -3 -m pip install pyserial
py -3 deploy/p10_readonly.py ports
py -3 deploy/p10_readonly.py inspect --port COM7 --vid 0x1234 --pid 0x5678 --serial-number NEW-P10-SERIAL --baud 115200 --isolated-host-confirmed --out C:/Workspace/.analienx/sonoff-private/issues/p10/p10-usb-identification.json
```

Replace COM7, VID, PID and the USB serial number with values printed by `ports` (if no serial number is exposed, use `--usb-location` with its exact bus location) for the physically identified **new** unit; example IDs are placeholders and deliberately fail unless they match. Matching VID/PID identifies only the USB bridge, not the P10 board: check the unit label and owner independently. The script refuses to open an absent or changed USB port. The script opens only that port, deasserts DTR/RTS before opening it, and sends **only ZNP SYS_PING and SYS_VERSION**. Opening some USB serial bridges may still change DTR/RTS momentarily at the OS/driver level; avoid a production coordinator regardless. Baud options: 115200, 460800, 921600; select the vendor-documented rate. The script never retries other ports automatically or resets the chip. A failed response is `UNKNOWN`, not proof that the firmware is unsupported. Preserve the original factory image; do not flash during this stage. The output stores no IEEE addresses or keys. Never publish raw serial logs or network backups.

## 2. Firmware/image audit

The response is a firmware-reported ZNP version, **not** a vendor-unique build hash and not a table-capacity query. Copy the exact vendor image to a private staging directory only if there is a provenance-verified download. Fingerprint a local file without modifying it:

```powershell
py -3 deploy/p10_readonly.py artifact C:/path/to/EXACT-vendor-P10-coordinator.hex
py -3 deploy/p10_firmware_audit.py docs/p10_firmware_candidates.json --image C:/path/to/EXACT-vendor-P10-coordinator.hex --target-board SLZB-06P10 --min-neighbor 60 --min-tclk 100
```

Select `--target-board` only after reading the exact physical model (use SLZB-06P10U or SLZB-MR4U instead when appropriate). Update the candidate manifest only with values from the **exact image's** build configuration, map file or documented vendor confirmation (record each table's `proof`, HTTPS `evidence_url`, `image_sha256` and exact local image hash, source, version and board revision). This script checks *metadata completeness and actual bytes of the specified local image*, not the truth of the asserted capacity nor that this image runs on the USB device: independently inspect linked source/build evidence before proceeding. Missing values return `BLOCKED` and exit code 3; matching locally hashed image plus valid metadata returns `MANIFEST_FIELDS_COMPLETE_UNVERIFIED` and exit code 4. Both are NONZERO deliberately: manual source/build provenance review and isolated functional gates are still mandatory. Neither permits migration. `MAX_NEIGHBOR_ENTRIES=50` in a *different* CC2652P7 build does not prove a P10 image is configured likewise. Standard Mgmt_Lqi responses show current neighbor entries, not allocated maximum. Phase A records six distinct tables (direct neighbors, TCLK, link keys, children, routing, source routes). Groupcast, unicast, real neighbor relationships, backup restore and security frame-counter monotonicity are separate later physical/migration gates: Phase A never marks production migration ready. Successful USB identification alone is never a capacity measurement or a migration decision. `--min-tclk 100` is a provisional conservative planning threshold, **not** a claim that every joined router consumes one TCLK record. Determine the actual backup key-record demand privately without publishing keys.

## 3. Candidate comparison / public evidence

- **Factory SMLIGHT P10 coordinator image:** inspect and preserve first. Board-level fit is strongest, but no exact-build direct-neighbor/TCLK capacities have been verified for our purchased unit. Firmware *bridge/UI* version is not the CC2674 Zigbee firmware version.
- **Latest SMLIGHT P10 image offered to the exact board:** consider only after checking its release notes, binary hash, secure fallback/bootloader and actual table allocation. A version reported on an MR4U, 07P10 or a SONOFF PP10 is **not** automatically available or compatible with a 06P10.
- **Koenkk `20250321`:** release notes mention an attempted `BUFFER_FULL` fix and SimpleLink SDK 8.30.01.01, but the published CC2674P10 binary is marked WIP/unavailable. Never flash the CC2652P7 image onto a CC2674P10.
- **Koenkk `20240710` / `20221226`:** useful Z-Stack regression histories, **not verified P10-compatible flash candidates**.
- **SONOFF Dongle-PP10 stock `20250321`:** not SMLIGHT hardware firmware. A public ~75-device restore reported `tclk table size insufficient (size=40)`; a separate groupcast `NWK_NO_ROUTE` report exists. Treat these as P10 test requirements, not as proof of the SMLIGHT firmware's capacities.

Sources: https://github.com/Koenkk/Z-Stack-firmware/releases ; https://github.com/Koenkk/Z-Stack-firmware/discussions/545 ; https://github.com/Koenkk/zigbee2mqtt/issues/32885 ; https://www.zigbee2mqtt.io/guide/adapters/zstack.html ; https://software-dl.ti.com/simplelink/esd/simplelink_cc26x2_sdk/2.30.00.34/exports/docs/zstack/html/zigbee/znp_interface.html

## 4. Gates before any migration

1. Exactly identified product/board revision, ZNP revision and source-backed firmware SHA; evidence of **>=60 stable direct-router capacity**, including bidirectional Link Status across more than 26 entries; enough security, route and source-route capacity for the private backup.
2. A separate disposable network that tests 60+ independently verified, simultaneously reachable routers, groupcasts, unicast retries, joins and power-monitoring traffic. Mgmt_Lqi pagination must not be confused with capacity. Capture actual routing and delivery metrics with fixed devices and equal windows.
3. Written rollback, network-state migration validation, security frame-counter monotonicity, Zigbee2MQTT entity compatibility and no forced mass repair. Cross-stack Ember -> Z-Stack backup transfer is not guaranteed; do not overwrite the current SONOFF backup or presume same-stack migration guidance applies.

**No automatic firmware selection or flashing is implemented.** The audit intentionally returns `BLOCKED` until exact-build evidence and an isolated validation exist.

## 5. Additional version-specific findings (2026-09-23)

The public **SMLIGHT** P10 image lineage is broader than the Koenkk release list. A July 2026 issue shows an SLZB-06P10 running radio build `20240716` with core/ESP bridge `v3.3.1`; another July report shows an SLZB-06P10 radio `20240705` in a 115-device network with `NWK_TABLE_FULL` after router power cycling and low *ESP32 host* heap. The ESP32 host heap must **not** be confused with CC2674P10 radio heap. In an August 2026 Zigbee2MQTT issue, an SLZB-06P10 was running radio `20260310` and core `v3.3.1`. An independent July forum report describes **development/beta** radio `20260311` (115200 baud, SDK 8.32.00.07) and a positive nine-day observation, which is anecdotal and not table-capacity evidence. A SMLIGHT upstream firmware manifest diff also refers to revision `20250201`, but the exact firmware's board applicability and resources need confirmation. **Do not equate radio revision with SMLIGHT core/ESP firmware v2.x/v3.x.**

Firmware evaluation priority: (a) preserve and inspect the *actual factory image*; (b) compare the latest **stable, exact-board SMLIGHT radio firmware** after finding its release notes and SHA; (c) retain `20260310` as a contemporary reference and `20260311` as a separately tested beta possibility, not an automatic upgrade. Older `20240705`/`20240716` and `20250201` are compatibility/regression reference points. Do not downgrade to any image lacking a verified P10 recovery path. The observed SONOFF PP10 groupcast/TCLK incidents are tests to replicate, not proof about SMLIGHT builds.

Relevant dated reports: https://github.com/Koenkk/zigbee2mqtt/issues/32751 (radio 20260310); https://github.com/Koenkk/zigbee2mqtt/issues/32706 (radio 20240716); https://github.com/Koenkk/zigbee2mqtt/issues/32667 (radio 20240705, host heap distinct); https://forum.iobroker.net/topic/84679/zigbee-adapter-mit-lan-dongle-kein-automatisches-verbinden/17 (20260311 beta); https://github.com/home-assistant/core/issues/165159 (SMLIGHT reported latest-version value can be stale). Confirm exact target board and firmware artefact before any flash.

## 6. Neighbor-table proof — what the scripts actually establish

`deploy/p10_neighbor_capacity.py` is an OFFLINE parser. It does not open serial ports, send ZDO management requests, form/join a network, or read an existing household backup. Its two inputs MUST NOT be mistaken for the same kind of evidence:

```text
python deploy/p10_neighbor_capacity.py macro C:/private/preprocessed-macros.txt --image C:/private/exact-p10-radio.hex
python deploy/p10_neighbor_capacity.py snapshot C:/private/isolated-znp-lqi.json --image C:/private/exact-p10-radio.hex --min-neighbor 60 --out C:/private/p10-neighbor-summary.json
```

The `macro` file must be a **compiler-preprocessed `-dM` macro dump** from the exact P10 coordinator build, not a raw header or a different board's config. The script requires exactly one literal `MAX_NEIGHBOR_ENTRIES` definition, hashes both supplied files and reports the *declared configured value*. It explicitly marks the macro-dump→image linkage and running-device image identity **UNVERIFIED**. An ELF/map or vendor-signed build manifest must establish that linkage; the script does not manufacture it. A stock radio `.hex` without source/symbol evidence cannot reliably yield this maximum by USB SYS_VERSION or hex-string searching.

The `snapshot` input must be a **private**, explicitly isolated/disposable network capture, collected later under a separate approval using only the test coordinator and test routers. Expected JSON has `scope="isolated-disposable-network"`, `observer_role="coordinator"`, `source="ZDO-Mgmt_Lqi_rsp"`, the SHA-256 of the supplied local radio image, and a chronological `captures` array. Each capture has `timestamp_utc` (offset-aware ISO-8601) and `pages`; each page should be `{ "znp_frame_hex": "<complete FE... FCS-checked TI ZNP 0x45/B1 response>" }`. The alternative decoded form requires `status`, `neighbor_table_entries`, `start_index`, `neighbor_table_list_count`, and `entries` containing each neighbor's `ieee` (private only), `device_type`, `rx_on_when_idle`, `lqi`. Do not mix decoded and raw response data to bypass validation.

The parser requires complete gap-free pagination, consistent totals, unique non-sentinel IEEE values, success status, 22-byte neighbor records (for raw ZNP), exact response length and FCS. It counts only Router (`device_type=1`) entries with RX-on-when-idle (`=1`). The output contains **counts only**, not IEEE addresses. Even with 60 entries in a complete multi-page response, a table could change between pages while preserving the total: this is *reported paged occupancy*, NOT an atomic observation of 60 simultaneous entries, a compiled maximum, bidirectional Link Status, or successful routing. A pinned isolated owner-local neighbor-table snapshot or equivalent stack instrumented test is still required for that stronger claim.

### Exact maximum: required vendor/build evidence

Request from SMLIGHT for **the physical board revision and its exact radio `.hex` SHA-256**, not an ESP32/SLZB-OS firmware version: (1) SDK/Z-Stack release and complete coordinator image build identifier; (2) effective compiled `MAX_NEIGHBOR_ENTRIES` and any distinction between physically allocated slots and active entries; (3) preprocessed build macros, linker `.map`/ELF DWARF symbol and neighbor structure dimensions, or a documented vendor capacity statement explicitly tied to that image hash; (4) same-image Trust Center link-key/TCLK, child, route and source-route sizes; (5) whether neighbor indices, admission/eviction/aging, multi-frame Link Status, ZDO Mgmt_Lqi pagination, route and security handling function correctly beyond 26 direct routers. Ask if 60 direct neighbors are intentionally supported or whether a lower direct-neighbor count is the validated design for a 60-router mesh. A generic chipset RAM figure, `SYS_VERSION`, a source header from another build or a snapshot of 60 distinct routers seen *across time* does not resolve this.

Neither the public SMLIGHT ESP32 bridge firmware sources nor third-party CC2652P7 macro settings establish the radio tables in a stock CC2674P10 image. A vendor-provided image may be binary-only; if so, keep the exact configured maximum as **UNKNOWN** until hash-tied vendor evidence or a properly instrumented independent build/test is available. Do not invoke a bootloader or firmware readback on the new coordinator merely to collect Phase A identification: those modes may reset it and are outside the read-only `SYS_PING`/`SYS_VERSION` probe.

## 7. Existing-mesh P10 capacity gate — no replacement test routers

`deploy/p10_capacity_gate.py` compares **the actual retained `zigbee2mqtt/bridge/devices` inventory** with proposed **exact-image compiled table allocations** and measured private table demand. It does not scan or modify the production mesh, open the dongle, trigger Mgmt_Lqi/networkmap requests, or create a second network. It never prints Zigbee IEEE identifiers or key bytes. Store input files privately; only sanitized output should be shared.

```powershell
py -3 deploy/p10_capacity_gate.py --inventory C:/private/p10/z2m-bridge-devices.json --image C:/private/p10/exact-P10-radio-image.hex --capacity-evidence C:/private/p10/exact-build-capacity.json --neighbor-reserve 8 --out C:/private/p10/capacity-summary.json
```

The inventory is the already-retained MQTT `zigbee2mqtt/bridge/devices` JSON array, **not a fresh network map**. The evidence JSON has `radio_image_sha256`, `compiled_tables` (integer `neighbor`, `tclk`, `link_keys`, `children`, `routing`, `source_routes`), plus *privately measured* `private_tclk_demand`, `private_link_key_demand`, `private_direct_child_demand`, `private_route_demand`, `private_source_route_demand`. These fields are demands from actual network-state records, **not router counts or guessed entries per router**. The exact number of direct neighbors needed can be smaller than the number of mesh routers. This strict optional policy instead insists that the configured table can accommodate all routers directly plus a reserve; if the policy is not met, it is a **policy FAIL**, not proof that a multi-hop network is impossible.

`CLAIMED_SUFFICIENT` is **never proof**. A SHA-matching manifest can be written by anyone; a preprocessor macro is not itself linked to the shipped firmware; SYS_VERSION does not expose the runtime table allocation. Source/ELF/map evidence, binary/linker provenance, and actual running-image identity must be independently corroborated. The script explicitly returns `NOT_PROVEN` (exit 3) instead of authorizing migration; known below-policy tables return `FAIL` (exit 4); invalid/private/missing input returns exit 2. No result can authorize production migration on its own. **Do not weaken the gate by setting invented capacity or key-demand values.**

After a separately validated, reversible Ember-to-Z-Stack cutover, `--operational C:/private/p10/existing-mesh-24h.json` evaluates the **same actual routers** for at least 24 hours, at least 20 attempted application transactions per router, >=99% aggregate delivery, >=95% delivery per router, <=1 source-route failure per 1000 attempts, zero reported capacity-exhaustion events, and explicit bidirectional-link and groupcast observations. It reports `OBSERVED_PASS` for a qualifying *finite test window*, never guarantees future radio performance or establishes the compiled maximum. Raw logs/samples and test provenance require external verification; handwritten JSON must not be treated as independent measurement. Existing 60+ routers are used **only after controlled cutover**, never concurrently paired to a test coordinator. Successful firmware-capacity evidence and full network-state transfer/rollback remain separate prerequisite gates.

## Actual USB preflight — 2026-09-23, MR4U, isolated Zephyrus

The freshly attached **SLZB-MR4U** enumerated as two USB CDC serial interfaces on the laptop. The existing read-only `p10_readonly.py inspect` (SYS_PING and SYS_VERSION only, 115200 baud) successfully identified **COM4** as TI ZNP; the other serial interface was **not probed**. The TI radio responded with `transport_rev=2`, `product=1`, version `2.7.1`, build revision **20240705**, and one uninterpreted extension byte `00`. The original strict parser rejected the valid 10-byte response; regression coverage now accepts 5, 9, or 10 bytes, preserving the final byte without inventing its meaning. The timestamped result is held in the existing private P10 evidence folder and must not be committed or published together with USB serial numbers or coordinator identifiers.

**Capacity verdict: NOT PROVEN.** SYS_VERSION exposes neither allocated `MAX_NEIGHBOR_ENTRIES` nor Trust Center/security, association, route, or source-route capacities. Build revision `20240705` is not a cryptographic identity of the running firmware, nor evidence that a similarly numbered firmware for a different board is identical. Do not run the production migration gate as PASS on this result. The 63-router network remains active on SONOFF, and this Phase A step used no NV reads, bootloader access, firmware writes, network creation, joins, or production radio operations.

Next evidence: obtain the exact MR4U P10 factory firmware's image and linked build/map, verify its provenance against the running radio, quantify independently allocated neighbor/child/security/route tables and actual key-record demand, then plan a reversible cutover to measure the existing network. A nominal chip RAM size or 60+ total routers spread across hops cannot establish 60+ *direct* neighbor capacity.
